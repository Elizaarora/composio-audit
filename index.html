The Headline

77% of these apps authenticate with OAuth2 or a plain API key — the mechanics of authentication are rarely what blocks agent integration. What blocks it is approval: 44% of docs never state whether access is self-serve, because that’s a pricing-page question, not a docs-page one. The friction that does show up concentrates hard in two places: Marketing & Ads, where 4 of 10 apps need a manual platform review (Google, Meta, LinkedIn, Threads all gate production access behind human approval), and enterprise data platforms, where both fully Blocked apps (iPayX, PitchBook) sit. 83 of 100 apps are buildable as agent tools today with no blocker at all.

The Agent

A two-pass, Composio-grounded research pipeline

The obvious first draft — ask an LLM what auth an app uses — produces confident, plausible, sometimes-wrong answers from training data. Every answer here is instead extracted from a real fetched page, with an explicit instruction to say “unclear” rather than guess.

01 · Fetch
Composio COMPOSIO_SEARCH_FETCH_URL_CONTENT pulls the given docs hint as clean markdown.
→
02 · Extract
Gemini fills the schema only from that fetched text — unsupported fields must say “unclear,” never guess.
→
03 · Confidence check
Thin fetch, low self-rated confidence, or an unclear core field → escalate. Happened for 93/100 apps.
→
04 · Search & re-fetch
Composio COMPOSIO_SEARCH_TAVILY finds a better URL; its own returned text is reused directly.
→
05 · Re-extract
Same grounded extraction over the combined text becomes the final answer.
# the actual Composio SDK calls, from tools.py
client.tools.execute("COMPOSIO_SEARCH_FETCH_URL_CONTENT", {"urls": [url]}, user_id="default")
client.tools.execute("COMPOSIO_SEARCH_TAVILY", {"query": query, "max_results": 5}, user_id="default")

Where a human was needed

  • Setting the escalation trigger — the thin-page threshold and which fields count as “unclear enough” to justify a second pass is a judgment call about where grounding effort pays off.
  • Reading the verification sample’s real docs — the agent’s own confidence score isn’t proof; someone has to actually open the page and check.
  • Judging ambiguous gating — an app with a public API that still needs a sales call for production keys is a call the schema can’t fully automate.
  • Catching the has_mcp false positives — a targeted spot-check, not the pipeline itself, found this field unreliable (see verification).
  • A platform-level surprise — this machine’s Windows Application Control policy blocked the grpc native binary the official Gemini SDK depends on. The fix (call the Gemini REST API directly instead) needed a human to diagnose, not just retry.

Resilience by design

  • No Composio key, no problem — tools.py falls back automatically to a free, no-key implementation (direct HTTP fetch + Bing HTML search) behind the identical function signatures. Every result records which backend produced it.
  • Two full runs exist — an earlier 100-app pass on the free fallback is kept in the repo (data/baseline_direct_run/) alongside this Composio-grounded one, for comparison.
  • Checkpointed — results save every 10 apps, so a crash mid-run loses at most 10 apps of work, not the batch.
The Verification

Did the grounding loop actually help?

A stratified sample — 2 apps per category, 20 total — was checked independently: real docs fetched separately from the pipeline itself, then compared field-by-field against what the agent said after pass 1 and after the full grounding loop.

What the agent got wrong

MissMeta Ads, Threads (Meta) — api_surface

Labeled Meta's 'Graph API' as 'GraphQL'. They're not the same thing -- Meta's Graph API is a REST-like custom API that predates and isn't built on the GraphQL query language spec. A plausible name-based confusion, wrong both times it occurred.

MissJira — auth_method

Final answer lists six auth methods (Basic auth, OAuth, OAuth 1.0a, OAuth 2.0, Personal access token, Cookie-based) as if all apply to Jira uniformly. Several of those (OAuth 1.0a, PATs, cookie-based auth) are Jira Server/Data Center specific, not Jira Cloud REST API methods -- the pass-2 search pulled a generic Atlassian auth overview covering multiple deployment types instead of one scoped to Jira Cloud.

MissSmartsheet — gating

Final answer claims 'Self-serve (paid/trial)' but neither the agent's own fetched text nor an independent check of Smartsheet's docs states pricing/access terms. This is the one case in the sample where the model appears to have asserted more than its source text actually supported, instead of saying 'Unclear.'

MissPitchBook — evidence_url

Pass-2 search surfaced dlthub.com's community data-connector docs (a third-party integration guide) rather than any PitchBook-official source, and the agent cited it as evidence. The final verdict (Blocked, partner-gated) happens to be correct -- PitchBook genuinely has no self-serve API -- but the auth_method claim ('API key') is sourced from an unofficial reverse-engineered connector, not PitchBook's own docs.

Field flagged unreliablehas_mcp

The pipeline flagged 27 of 100 apps as having a mentioned MCP server. This field was NOT part of the 20-app stratified sample, so it got a separate targeted spot-check: 3 of the 27 'Yes' claims (Pumble, fanbasis, and Coda) were checked directly against their own cited evidence URLs. Two were confirmed false -- neither Pumble's nor fanbasis's cited page mentions MCP at all. The third (Coda) couldn't be re-checked at all because its evidence URL now redirects elsewhere. This is a real, disclosed limitation: has_mcp should be read as 'the model's exploratory guess, unreliable,' not a verified finding, and the 27-app figure is not trustworthy as reported. Likely cause: MCP is widely enough discussed in 2026 that the model leans toward inferring it even from adjacent context (automation/integration language) rather than an explicit statement.

What the grounding loop actually fixed

Fixed by pass 2Pylon

Pass 1 incorrectly claimed 'Partner/contact-sales gated' with no supporting evidence. Pass 2 corrected this to an honest 'Unclear from fetched text' -- a real self-correction, not just a lucky guess.

Fixed by pass 2DataForSEO

Pass 1 left auth_method unclear; pass 2 correctly resolved it to 'Basic auth' (HTTP Basic Auth using the account login as username), confirmed independently.

Fixed by pass 2YouTube Transcript

Pass 1 left gating unclear; pass 2 correctly resolved it to 'Self-serve (free)', matching the vendor's own '100 free credits, no card required' language.

Fixed by pass 2WooCommerce

Pass 1 was already fully correct on all three fields (no pass 2 needed) -- confirms the escalation trigger isn't firing needlessly when a hint page already has the answer.
